# 结算对账与生产部署复盘：一单货到了之后，钱怎么算清楚

走到这里，一单货的物理旅程已经结束：下单、计费、分类、寻路、配车、发车、在途监控、签收。但在物流公司的账上，事情还没完——**货送到了，钱还没算清。** 向客户收多少、给司机结多少、和外协承运商怎么对账，这些构成了 TMS 的财务闭环。

这是系列的最后一章。我先讲签收后怎么自动生成结算单，再把整个系统做一次生产部署复盘——这套代码哪些地方是真功夫、哪些是待还的债、二开该往哪走，一次说透。

## 签收不是一个调用，而是一个领域事件

先看触发方式。司机/快递员在移动端签收后，`pd-web-courier` 并不直接调结算服务的接口，而是发布一个领域事件 `ORDER_DELIVERED` 到 RabbitMQ 的主题交换机，结算服务自己订阅消费。监听器在 `pd-oms`：

```java
@RabbitListener(bindings = @QueueBinding(
        value = @Queue(value = "xinfei.oms.queue.order.delivered", durable = "true"),
        exchange = @Exchange(value = "xinfei.domain.event.exchange", type = "topic", durable = "true"),
        key = "ORDER_DELIVERED"))
public void onOrderDelivered(String message) {
    OrderDeliveredEvent event = objectMapper.readValue(message, OrderDeliveredEvent.class);
    if (!event.isSigned()) { /* 拒收不产生应收结算 */ return; }
    if (!event.isNeedSettlement()) { /* 标记无需结算则跳过 */ return; }
    settlementService.settle(event.getOrderId(), event.getTransportOrderId());
}
```

为什么签收和结算之间要用事件解耦，而不是直接调一下？因为"订单签收"是一个会被多个域关心的业务时刻：财务要结算、调度要更新任务、消息服务要给客户发短信通知、积分系统可能要给会员加分。如果签收接口里硬编码一个个去调这些下游，任何一个下游变慢或挂掉，都会拖垮甚至回滚签收这个核心动作。用领域事件广播，各域各取所需、互不影响，将来加新订阅方也不用动签收代码。

这个监听器的注释还记录了一段很真实的微服务边界治理。原来 `pd-dispatch` 里有个 `OrderEventListener` 想在签收时顺便调结算，但那个调用后来被注释掉了、结算服务本身也缺失。按领域边界，结算本就该归 `pd-oms`，于是改造者没有去动调度模块、也没复活那段越界代码，而是在 `pd-oms` 新建独立队列消费同一个事件（消息按队列各存一份，互不影响），注释写明"语义等价"。**宁可多一个订阅，也不让调度域重新背上财务域的职责**——这种对边界的克制，比写出新功能更见功力。

## 独立事务 + 幂等：绝不让算账拖累签收

真正的结算逻辑在 `SettlementServiceImpl.settle`，两个设计值得专门讲。

**第一，结算用独立事务，失败绝不影响签收。**

```java
@Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
public void settle(String orderId, String transportOrderId) {
    try {
        doSettle(orderId, transportOrderId);
    } catch (Exception e) {
        // 结算异常只回滚结算这一个新事务，不向外抛，签收主流程不受影响
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
    }
}
```

`REQUIRES_NEW` 让结算挂起外层事务、开一个全新事务执行。这样万一算钱时出任何岔子，回滚的只是结算自己，签收这个已经真实发生、不可逆的业务事实纹丝不动。这和第 7 章交付确认里用 try-catch 包住状态联动是同一个信念：**物理世界已经完成的动作（货到了、人签收了）不能因为后台某个记账失败就被系统判为没发生。** 结算失败了怎么办？靠日志告警 + 事后补偿重放，而不是阻断当下。

**第二，结算必须幂等。** 因为它有两个触发来源——上面的 MQ 事件，以及签收更新时的一个同步兜底点（防止 MQ 抖动消息丢失）。两条路都可能触发 `settle`，绝不能生成两张结算单。做法是经典的"先查后建"：

```java
// 幂等：结算单已存在（重复交付事件 / 重复状态更新）直接返回
SettlementOrder existing = settlementOrderService.getOne(
        new LambdaQueryWrapper<SettlementOrder>().eq(SettlementOrder::getOrderId, orderIdValue));
if (existing != null) { return; }
```

查到已存在就直接跳过，数据库层再用唯一索引兜底并发。注释把这个组合概括为"先查后建 + 唯一索引"。凡是"可能被重复触发的写操作"，幂等都不是可选项。

## 两张单据：运费明细与结算单

幂等确认后，`doSettle` 落两类数据。

先是**运费明细 `FreightDetail`**：最小闭环阶段，一单先落一条费用项为"运费"、金额等于订单总价的明细。但这个结构是为细化计费预留的——注释写得明白，等 Drools 规则扩展后，可以在这里把一单拆成首重费、续重费、保价费、上楼费、包装费等多条明细，每一条有数量、单位、单价、金额。明细与总额分开存，财务对账单才能让客户看明白每一分钱。

再是**结算单 `SettlementOrder`**，这是财务域的核心单据，字段很能说明问题：

```java
settlement.setSettlementNo("STL" + settlementId);        // STL + 雪花单号
settlement.setSettleObjectType(SettlementOrder.OBJECT_MEMBER); // 对象类型：客户
settlement.setSettleObjectId(order.getMemberId() == null
        ? SettlementOrder.GUEST_OBJECT_ID : String.valueOf(order.getMemberId())); // 散客兜底
settlement.setDirection(SettlementOrder.DIRECTION_RECEIVABLE); // 应收方向
settlement.setPeriodStart(now.toLocalDate());            // 账期起止
settlement.setPeriodEnd(now.toLocalDate());
settlement.setOrderCount(1);
settlement.setReceivableAmount(amount);                  // 应收
settlement.setPayableAmount(BigDecimal.ZERO);            // 应付
settlement.setSettledAmount(BigDecimal.ZERO);            // 已结算
settlement.setStatus(SettlementOrder.STATUS_PENDING);    // 待对账
```

结算对象分三类：客户、司机、承运商（外协/加盟），用 `settleObjectType` 区分；资金有 `direction` 方向——向客户是应收（RECEIVABLE），给司机和承运商是应付（应付方向字段也已备好）。单据状态走"待对账 → 已对账 → 已结算"三步：待对账是刚生成等财务核对，已对账是和客户/司机确认了金额，已结算才是钱真正结清，`settledAmount` 记录已结金额。没有会员账号的散客用一个 `GUEST` 兜底标识，避免非空约束写挂。单号用"STL + 雪花"前缀，肉眼一看就知道这是张结算单。

要分清结算单和前面出现过的支付单 `PaymentOrder`：支付单回答的是"这笔钱实际收没收到、走的什么渠道"，是资金流水视角；结算单回答的是"该收谁多少、该付谁多少、对没对账"，是债权债务视角。两者配合才完整。

我也要诚实说明这一版的边界：它实现的是**最小闭环**——签收后自动生成对客户的应收结算单，金额直接取订单总价；给司机、承运商的应付结算还在数据模型上预留了字段、尚未铺开逻辑。而真实的微信/支付宝收款、数电票开具、银行付款，代码注释明确写了"均由外部渠道网关对接，本服务只生成内部应收单据，不触达任何外部资金/税控接口"——这些需要支付牌照和税控资质，不是一套开源代码该越界碰的。这个边界划得非常清醒。

## 生产部署复盘：这套代码教会我的事

十个模块读下来、改下来，最后做一次复盘。

**先记教训：文档不能全信。** README 两处描述和代码对不上——轨迹管道写的是 Kafka，实际是 RabbitMQ；定时调度写的是 Quartz，实际 2026 年 10 月已迁到 XXL-Job。我第一次部署时就因为信了 README、漏起 XXL-Job，导致所有服务正常但调度一动不动。结论在前面说过，这里再强调一次：以能编译运行的代码和自动化配置为准，文档只当导游图，不当施工图纸。

**中间件是硬门槛，启动有严格顺序。** 这套系统强依赖 Nacos、MySQL、Redis、RabbitMQ、XXL-Job 五件套，外加 pd-netty 单独暴露的 TCP 端口。必须先起基础设施、导完各域建表脚本，再按 `pd-base → pd-auth → 业务服务 → pd-gateway` 的顺序拉起，最后在 XXL-Job 控制台为每个机构配置 `dispatchTask` 任务（参数填机构 ID）。脱离了这些，单个服务再正确也是孤岛。

**最值得带走的，是这一版生产化改造留下的一整套工程范式。** 我把它们汇总在这里，几乎每一条都能迁移到你自己的项目：

- 状态码从稀疏五位码收敛为紧凑 TINYINT，并强制所有调用走枚举常量，为重构买保险；
- 用"状态条件更新"实现乐观锁，配合显式状态机校验和流转审计表，并发与可追溯兼得；
- 批处理外层故意不加事务、内层各自成事务，避免 rollback-only 引发 `UnexpectedRollbackException` 毁掉错误日志；
- 系统态线程（定时任务、MQ 消费、离线扫描）一律手动绑定租户、`finally` 清理，严防线程池复用导致串租户；
- 单条脏数据 try-catch 隔离，绝不让一单失败拖垮整轮几千单；
- 告警阈值全部外部化到配置，立"禁止硬编码"红线；
- 轨迹冷热分离、分批 5000 归档删除，避免大事务锁表；
- 所有可能重复触发的写操作做幂等，关键业务动作配独立事务与补偿。

**当然也还有待还的债，这正是你二开的价值所在。** Drools 规则里还留着 `System.out.println`、规则内 `new` 服务、续重向下取整少算钱的问题（第 3 章）；DFS 的访问集合只增不减可能漏路径、缺深度上限（第 6 章）；偏航检测对照的是历史点而非规划线路，不是严格意义的电子围栏（第 9 章）；应付司机和承运商的结算还没落地；JT/T 808 北斗终端协议也只留了扩展位。这些不是劝退的理由，恰恰说明它是一个"骨架真实、留足空间"的好底座——真正有壁垒的业务规则，本来就该由在一线的你补上去。

## 系列终章：从一单货看懂一套系统

回头看这十章，我们其实是跟着一票货走完了完整一生：它在 `pd-oms` 下单、被 Drools 算出运费、挂上 12 态状态机；在 `pd-dispatch` 被分类、被 DFS 寻出中转路径、被匹配到最合适的车次车辆司机；在 `pd-work` 生成运输任务，靠乐观锁安全地完成发车、到达、交付；在 `pd-netty` 被数千个 GPS 点实时追踪、自动识别四类异常；最后在签收的那一刻，由一个领域事件触发 `pd-oms` 生成应收结算单，财务闭环。一条主线，串起了微服务架构、图搜索、规则引擎、状态机、并发控制、长连接通信、消息队列、流式计算和数据冷热分层——这正是我偏爱 TMS 这个题材的原因，它是后端技术的一个高密度练兵场。

我做这套"行业卡片"的初衷也始终没变：比起从零造轮子，读懂一个真实开源项目的设计意图、看清它的好与烂、再动手把它改成能上生产的系统，是成长最快的路径。仓库在 `itxinfei/pinda-tms`，Apache-2.0 协议，我所有改造都从一个 `v0-baseline` 标签起步，建议你也 clone 一份，边读边 diff。

仓库管理完，下一张卡片我会去更上游的地方看看——供应链计划（APS），回答"该在什么时候、备多少货、排什么产"的问题。那是比运输调度更靠前、也更难的决策问题，我们到时再见。
