# 告警与归档：四类异常检测与轨迹冷热分离

GPS 点位进了库、在地图上画出移动的小车，这件事本身并不产生价值。车队长真正关心的是另一组问题：**有没有车在超速？有没有车在半路异常停了几个小时？有没有车偏离了既定路线？哪些车已经失联？** 如果这些还要靠人盯着屏幕看，系统就只是个昂贵的播放器。

这一章讲轨迹数据的两种"增值加工"：一是在点位流上实时做四类异常检测并告警，二是用冷热分离让几百万乃至上亿条轨迹不至于把数据库拖垮。两块都在 `pd-netty` 里，代码量不大，但处处是生产环境打磨过的细节。

## 检测时机：在数据流上"滑动"着判断

异常检测发生在消费端。上一章看到，每消费一个新点位，`checkAnomalies` 就会被调一次，它依赖的是内存缓存里这辆车最近的一串轨迹点：

```java
private void checkAnomalies(LocationEntity location, String cacheKey,
                            List<LocationEntity> tracePoints) {
    if (tracePoints.size() < 2) {
        return;   // 只有一个点时连速度都算不出来
    }
    LocationEntity prevPoint = tracePoints.get(tracePoints.size() - 2);
    checkSpeed(location, prevPoint);            // 超速
    checkStayTooLong(location, cacheKey, tracePoints); // 长时间停留
    checkGeoFence(location, tracePoints);       // 偏离路线
}
```

这是典型的**流式滑动窗口**思路：不等数据攒齐，而是每来一个点，就拿它和最近的历史点在内存里即时判断。这也是为什么第 8 章要维护那个最多 5000 个键的 LRU 缓存——异常检测需要"最近一小段轨迹"作为上下文，而每辆车只保留最近若干点即可，过期的交给归档。下面逐个看四类告警。

## 告警一：超速，相邻两点反推瞬时速度

超速检测最直觉：用相邻两个点之间的距离除以时间差，反推这段路程的平均速度，超过阈值就报警。

```java
double distanceKm = calculateDistance(prevLat, prevLng, currentLat, currentLng);
long timeDiffSeconds = parseTimeDiffSeconds(current.getCurrentTime(), previous.getCurrentTime());
if (timeDiffSeconds > 0 && timeDiffSeconds < 300) {
    double speedKmh = (distanceKm / timeDiffSeconds) * 3600;
    if (speedKmh > speedLimitKmh) {
        gpsAlertService.alert("SPEED_OVER", current,
            String.format("超速提醒: 速度=%.1fkm/h, 阈值=%.0fkm/h, 位置=(%s, %s)",
                speedKmh, speedLimitKmh, current.getLng(), current.getLat()));
    }
}
```

这里有个很容易被忽略、但作者处理对了的细节：`timeDiffSeconds < 300`——**两个点的时间间隔必须在 5 分钟以内才参与测速**。设想车辆进了隧道，20 分钟没信号，出来后第一个点和隧道口那个点之间隔着几十公里，如果直接拿这两个点算，会得出一个离谱的"超音速"，全是误报。加一个间隔上限，就把这种"信号中断后瞬移"的情况排除了。这类"数据缺口不能当成真实运动"的意识，是轨迹处理的基本功。

## 告警二：长时间停留，时间和位移两个条件同时满足

车辆停车加油、司机休息是正常的，异常的是"在一个不该久留的地方停了很久"。检测方法是取最近一个滑动窗口内的点，同时判断时间跨度和位移：

```java
List<LocationEntity> recentPoints = tracePoints.subList(tracePoints.size() - checkSize,
                                                        tracePoints.size());
long stayMinutes = ChronoUnit.MINUTES.between(时间(首点), 时间(末点));
double lngDiff = Math.abs(末点lng - 首点lng);
double latDiff = Math.abs(末点lat - 首点lat);
if (stayMinutes > stayThresholdMinutes      // 时间超过 30 分钟
        && lngDiff < stayPositionThreshold  // 经度变化小于 0.001
        && latDiff < stayPositionThreshold) { // 纬度变化小于 0.001
    gpsAlertService.alert("STAY_TOO_LONG", ...);
}
```

两个条件缺一不可：只看时间，堵车也会触发；只看位移，等红灯也算停留。窗口取最近 `stayCheckWindow`（10）个点，时间跨度要超过 30 分钟，且经纬度变化都小于 0.001 度（约百米量级），才算"原地长时间停留"。这能识别出车辆抛锚、司机异常滞留这类需要调度主动联系的情况。

## 告警三：偏离路线，点到历史轨迹线段的距离

第三个检测 `checkGeoFence` 名字叫围栏，实际做的是轨迹偏离。它取当前点和前面两个点 `p1`、`p2`，把 `p1→p2` 连成一条线段，计算当前点到这条线段的垂直距离，超过阈值就认为偏离：

```java
double deviateKm = distancePointToSegmentKm(curLng, curLat, p1Lng, p1Lat, p2Lng, p2Lat);
if (deviateKm > deviateThresholdKm) {
    gpsAlertService.alert("DEVIATE_ROUTE", location,
        String.format("偏离路线提醒: 距历史轨迹%.1fkm, 阈值%.1fkm ...", deviateKm, deviateThresholdKm));
}
```

经纬度不是均匀的直角坐标，直接相减当公里数会错。代码先做了单位换算：纬度方向每度约 111 公里，经度方向每度的实际距离随纬度收缩，要乘上 `cos(纬度)`。然后是标准的点到线段垂足距离——把当前点投影到线段所在直线，投影参数 `t` 用 `Math.max(0, Math.min(1, t))` 钳制在 `[0,1]`，保证垂足落在线段内部而不是延长线上。这套几何计算是对的。

不过我要如实指出这个实现的局限：它比较的是"当前点"和"自己最近两个历史点连成的线段"，衡量的是**轨迹的突然突变**，并不是严格意义上对照"规划运输线路"的电子围栏。正常过一个大弯道、掉头，也可能短暂偏离历史线段。我二开时把它升级成了真正的围栏——从当前运输任务取出规划线路的几何（或司机手机端上报的导航路线），判断当前点是否在路线走廊（Route Corridor）的缓冲多边形内，这样"偏航"才名副其实。原实现作为一个轻量近似版，理解原理足够了。

## 告警四：车辆离线，不是消息触发而是定时扫描

前三类都是"来一个点算一次"，但离线恰好相反——**离线的特征就是没有点来**，你无法在消费消息时发现它。所以第四类靠定时任务：

```java
@Scheduled(fixedDelayString = "${gps.alert.offline-scan-interval-ms:60000}")
public void scanOfflineTrucks() {
    // 系统级扫描（非某消息触发），先绑定默认租户上下文
    TenantContextHolder.setTenantId(defaultTenantId);
    ...
    LocalDateTime threshold = LocalDateTime.now().minusMinutes(heartbeatTimeoutMinutes);
    // 最近心跳早于阈值的车辆 → 置离线并告警 VEHICLE_OFFLINE
}
```

默认每 60 秒扫一遍，哪辆车的 `last_heartbeat_time` 早于"现在减 5 分钟"，就判定失联、发 `VEHICLE_OFFLINE` 告警。这正好闭环了第 8 章那个设计原则——在线状态由心跳决定、不由 TCP 连接决定。注意方法开头那句租户绑定：这又是个没有请求上下文的系统级线程，得手动设置默认租户才能去查跨服务的车辆数据，和调度线程是同一类问题、同一套解法。

## 阈值一律外部化：一条"禁止硬编码"的红线

四类检测各有阈值，这版代码最让我欣赏的工程纪律，是把它们全部抽到了配置里，注释还标了红线编号：

```java
// ===== 以下阈值全部外部化到 gps.alert.* 配置（P0-5：红线"禁止硬编码阈值"） =====
@Value("${gps.alert.speed-limit-kmh:120}")        private double speedLimitKmh;        // 超速
@Value("${gps.alert.stay-threshold-minutes:30}")  private long stayThresholdMinutes;  // 停留时长
@Value("${gps.alert.stay-check-window:10}")       private int stayCheckWindow;        // 停留窗口点数
@Value("${gps.alert.stay-position-threshold:0.001}") private double stayPositionThreshold;
@Value("${gps.alert.deviate-threshold-km:2.0}")   private double deviateThresholdKm;   // 偏航距离
@Value("${gps.alert.heartbeat-timeout-minutes:5}")private long heartbeatTimeoutMinutes;// 离线心跳
```

为什么这条值得单独立红线？因为阈值是**因客户、因车型、因路况而异的运营参数**：危险品运输限速可能是 80，普货 100，厂区接驳车又是另一套；同一个客户的阈值还会随季节、政策调整。硬编码在 Java 里，每调一次都要改代码、测试、重新发版；外部化到配置（再进一步放数据库），运营改个配置就能生效。代码里每个 `@Value` 都给了默认值，则保证了"不配也能跑"的开箱体验。

## 告警出口：落库、推送与内容截断

四类异常最终都汇到 `GpsAlertService.alert`，它有三个出口，且都做了开关和容错：

```java
@Value("${gps.alert.enabled:true}")    private boolean alertEnabled;
@Value("${gps.alert.webhook-url:}")    private String webhookUrl;
private static final int ALARM_CONTENT_MAX_LENGTH = 255;
```

一是**落库**：告警写进 `iot_alarm_record` 表持久化，运营在后台能查、能确认、能处理（有 `AlarmController` 提供处置接口），告警不处理就一直挂着形成待办。二是**开关控制**：`gps.alert.enabled=false` 可以整体静音，方便测试或某些客户不需要时关闭。三是**可选的 Webhook 推送**：配了 `gps.alert.webhook-url` 就把告警 POST 到外部通知网关（可以转接钉钉、企业微信、短信）；没配就只落库记日志，不影响主流程。

还有个很细的点：告警内容在写库前被 `truncate` 截断到 255 字符，因为 `alarm_content` 列是 `VARCHAR(255)`。这不是多此一举——异常报文里万一带着超长的坐标串或异常字段，不截断就会在写库时抛 `DataTooLong` 异常，反而把整条告警搞丢。对外发数据前按目标字段长度裁剪，是对接存储时的防御性习惯。

## 冷热分离：热表只留 30 天，历史进归档表

最后解决数据量问题。按前面的估算，一千辆车一天就近 580 万点，一年是十亿级，全堆在一张 `location_record` 表里，查询和索引必然越来越慢。系统用了最经典的**冷热分离**：两张结构几乎相同的表，`location_record` 是热表只留近期数据，`location_record_archive` 是归档表存全部历史。

搬迁由定时清理方法 `cleanExpiredTraces` 完成，保留天数默认 30 天：

```java
LocalDateTime expireTime = LocalDateTime.now().minusDays(retentionDays);
int batchSize = 5000;
while (true) {
    wrapper.last("limit " + batchSize);
    List<LocationRecord> batch = list(wrapper);   // 分批查 5000 条
    if (CollectionUtils.isEmpty(batch)) break;
    archiveBatch(batch);                           // 1. 拷到归档表（保留原 id）
    removeByIds(batch.stream().map(LocationRecord::getId).collect(...)); // 2. 删热表
    if (batch.size() < batchSize) break;
}
```

它的处理是"查一批 → 归档到历史表 → 从热表删除"，每批 5000 条循环推进。为什么不一条 `DELETE WHERE create_time < ?` 全删？因为一次删几百万行会产生巨大事务、长时间锁表、撑爆 binlog，把在线服务卡住。分批处理把一次大锁化整为零，对线上影响可控。归档时保留原始 id 和全部字段、只额外打一个归档时间，历史追溯时主键都不变。另外保留天数配成 `<=0` 就跳过整个流程，等于可以关闭这个机制——给不同客户留了弹性。

这一版的归档表还是和热表同在一个 MySQL 里。如果量级继续涨，我会把冷数据再往下沉一层：按时间分区的表、对象存储（Parquet 文件），或者干脆进时序数据库/数仓，让热表始终保持苗条。**让高频访问的数据待在最便宜够快的地方，让低频的海量历史去便宜但慢的地方**，这就是冷热分离的全部哲学。
