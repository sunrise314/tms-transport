# 运单与运输任务：三个并行状态机与一条八字段时间轴

订单在 `pd-oms` 下完、运费算好，它还只是一个"商务合同"——客户和平台之间的一纸约定。真正要把货从 A 地搬到 B 地，靠的是作业域 `pd-work` 里的两类单据：**运单（TransportOrder）和运输任务（TaskTransport）**。

很多人初学 TMS 会被这三个概念绕晕：订单、运单、运输任务，到底有什么区别？这一章我就先把这三者的关系讲透，再重点拆运输任务这个实体——它是我认为整个系统里建模最讲究的一张表，用三个互相正交的状态机和一条八个字段的时间轴，把一趟公路运输管得滴水不漏。

## 订单、运单、运输任务：三个视角看同一趟货

先建立概念。这三者不是重复建模，而是三个不同视角下的单据：

**订单（Order，`oms_order`）是客户视角、商务视角。** 它回答的是"谁寄给谁、寄什么、多少钱"。一张订单从下单起就在 `pd-oms`，贯穿计费、支付、结算，主键是订单 ID。

**运单（TransportOrder，`work_transport_order`）是作业视角。** 订单一旦进入实际运输环节，作业域会为它生成对应的运单。它通过 `orderId` 反向关联订单，但归 `pd-work` 管理。为什么要多建一张表、不直接操作订单？因为两个域关心的东西完全不同：订单域关心钱和合同状态，作业域关心"这票货排进调度了没、运到哪了"。分表就是隔领域——调度系统高频读写运单，绝不该去打扰承载着金额的订单表。

**运输任务（TaskTransport，`work_task_transport`）是物理视角、车次视角。** 一辆车跑一趟，就是一个运输任务。关键在于它和运单是**一对多**：一辆干线货车从上海转运中心发往武汉，车厢里可能装着两百张运单对应的货。这两百张运单共用同一个运输任务，记录同一趟车、同一个司机、同一批时间点。你可以把关系记成一句话：**订单是一票货，运单是一票货的作业副本，运输任务是把很多票货装上车后的"一趟车"。**

运单实体很克制，字段不多：

```java
@TableName("work_transport_order")
public class TransportOrder {
    private Long id;
    private Long orderId;          // 关联的订单
    private Integer status;        // 运单自身状态
    private Integer schedulingStatus; // 调度状态
    private Long createBy;
    private LocalDateTime createTime;
    private Long updateBy;
    private LocalDateTime updateTime;
    private Integer deleted;
}
```

注意它有 `status` 和 `schedulingStatus` 两个状态字段：一个描述运单业务进度，一个描述它在调度系统里的处置情况（是否已被纳入某趟规划）。把"业务走到哪"和"调度处理到哪"分开，是因为这两条节奏并不同步——一张运单可能业务上还没装车，调度上却已经被预排进了明天的车次。

## 运输任务：三个互相正交的状态机

重头戏是运输任务。我把 `TaskTransport` 的核心字段按含义分组贴出来：

```java
@TableName("work_task_transport")
public class TaskTransport {
    private Long tripsId;          // 车次
    private Long startOrgId;       // 始发机构
    private Long endOrgId;         // 目的机构
    private Long truckId;          // 车辆

    // 任务状态：1待执行 2进行中 3待确认 4已完成 5已取消
    private Integer status;
    // 分配状态：1未分配 2已分配 3待人工分配
    private Integer assignedStatus;
    // 满载状态：1半载 2满载 3空载
    private Integer loadingStatus;
    ...
}
```

一个实体上挂了三个状态字段，初学者可能会问：为什么不用一个状态从头管到尾？答案是——这三个维度是**正交**的，谁也替代不了谁。

`status` 描述任务的**执行进度**：待执行 → 进行中 → 待确认 → 已完成（或取消），这是一条时间线上的主干。

`assignedStatus` 描述**资源分配情况**：未分配、已分配、待人工分配。为什么要独立？因为系统自动调度可能匹配不到合适的车或司机（比如这条线今天所有车都在外跑），这时任务不能卡在执行状态里干等，而要被明确标记为"待人工分配"，推到调度员的待办列表里。分配是调度瞬间的事，执行是之后几小时甚至几天的事，两者生命周期不同，必须分开。

`loadingStatus` 描述**装载程度**：半载、满载、空载。这个状态是给调度优化用的——如果一趟车空载或半载返回，系统就该考虑让它在返程捎上反向的货（回程车匹配），或者干脆合并车次。它既不是进度也不是分配，是一个纯粹的运营度量。

把三个正交状态拆清楚的好处是：任何一个维度变化都不污染另一个。"任务已完成但当时是半载""任务进行中且资源已分配"这类组合能被精确表达；如果硬塞进单一状态，你会得到一个状态值笛卡尔积爆炸的枚举（待执行未分配空载、待执行已分配半载……几十个组合），那才是灾难。这种"按正交维度拆状态"的手法，值得用在你自己的任何复杂业务实体上。

## 一条八字段时间轴：计划与实际的四次握手

运输任务上最能体现"运输是个时间敏感生意"的，是这八个时间字段：

```java
private LocalDateTime planDepartureTime;   // 计划发车
private LocalDateTime actualDepartureTime; // 实际发车
private LocalDateTime planArrivalTime;     // 计划到达
private LocalDateTime actualArrivalTime;   // 实际到达
private LocalDateTime planPickUpTime;      // 计划提货
private LocalDateTime actualPickUpTime;   // 实际提货
private LocalDateTime planDeliveryTime;    // 计划交付
private LocalDateTime actualDeliveryTime;  // 实际交付
```

四个关键节点——**发车、到达、提货、交付**——每个都有计划值和实际值一对。这套设计看着笨（占了八列），但它是运输考核和异常分析的数据金矿。

司机晚发车了吗？`actualDepartureTime - planDepartureTime` 一看便知。路上超时了吗？计划在途时长和实际在途时长一对比就有结论。晚点是发车就晚了、还是中途耽搁的？两个差值一比就能归因。我后来做的准点率看板、司机时效考核，数据源全是这八个字段，一行额外日志都不用加。

**把"计划"和"实际"成对落库，而不是只记一个实际发生时间**，是所有排程类系统的通用心法。计划值在调度阶段就写死了，实际值在司机手机端每次操作时回填，两者的差就是最诚实的运营度量。

## 交接环节的证据链：四张照片与两副坐标

运输任务上还有一组很"接地气"的字段：

```java
private String pickupPicture;      // 提货照片
private String cargoPicture;       // 货物照片
private String certificatePicture; // 凭证照片（回单）
private String deliverPicture;     // 交付照片

private BigDecimal pickupLongitude;
private BigDecimal pickupLatitude;   // 提货经纬度
private BigDecimal deliverLongitude;
private BigDecimal deliverLatitude;  // 交付经纬度
```

物流行业最怕的就是扯皮：货少了谁的责任？说送到了收货人不认怎么办？这组字段就是为了解决纠纷。提货时拍一张、装完货拍一张、签收回单拍一张、交到收货人手里再拍一张，四张照片串起完整的证据链；提货和交付两个动作还各记一副经纬度，用来核对"司机是不是真的到了指定地点操作的"，防止人在外地远程乱点签收。

这里有个值得一提的细节：经纬度用的是 `BigDecimal`，而不是 `double`。经纬度通常要精确到小数点后六位（误差在米级），浮点在反复运算和序列化时会有精度漂移，用 `BigDecimal` 存坐标是稳妥的选择。这和上一章金额用 `BigDecimal` 是同一个道理——**凡是对精度敏感、要原样存取的数值，别用浮点。**

## 主键、审计与一对多挂载

再看几个工程细节。主键是雪花算法分配的长整型，`@TableId(type = IdType.ASSIGN_ID)`，这在分布式系统里几乎是标配——多个服务、多个节点各自插入也不会撞 ID，还能从 ID 里粗略看出时间先后。删除是逻辑删除，`deleted` 字段配 `@TableLogic`，运输凭证这类涉及财务和纠纷的数据物理上绝不能真删。

运输任务和运单的绑定关系，体现在服务层一个很说明问题的方法签名上：

```java
@Transactional(rollbackFor = Exception.class)
public TaskTransport saveWithRelations(TaskTransport taskTransport,
                                       List<Long> transportOrderIds) {
    taskTransport.setStatus(TransportTaskStatus.PENDING.getCode());
    taskTransport.setAssignedStatus(TransportTaskAssignedStatus.TO_BE_DISTRIBUTED.getCode());
    taskTransport.setLoadingStatus(TransportTaskLoadingStatus.EMPTY.getCode());
    ...
}
```

新建任务时传进一串运单 ID，一次性把"一趟车 + 它装的两百票货"的关系在**同一个事务**里建好，初始三状态也在这里设好：待执行、待分配、空载。要么全部成功、要么全部回滚，绝不会出现"任务建了、运单却没挂上去"的中间态。而任务最终交付时，还会反向联动运单和订单的状态（第 7 章会看到 `syncStatusOnComplete`），让作业域的完成信号一路冒泡回订单域的"已签收"。

## 还有一类单据：司机作业单

运输任务是"车"的视角，但真正去提货、开车、交货的是司机这个"人"。所以第五阶段除了回填运输任务，还会生成一类司机作业单（`DriverJob`），由 `DriverJobServiceImpl` 管理，并通过移动端推到具体司机的待办里。

为什么有了运输任务还要司机作业单？因为两者的责任主体和粒度不同。运输任务描述的是"这趟车从 A 到 B"，而司机更关心"我今天要先去哪提货、几点发车、到了联系谁、交货时要收什么凭证"——这是一份按人的作业清单。一个司机当天可能被排了多个作业单，需要在手机上逐单处理；反过来，一辆车如果中途换司机，运输任务还是同一个，但作业单要重新指派。把"车的行程"和"人的待办"分成两类单据，调度在改派司机、统计司机绩效时才能各自操作，不会互相牵扯。

至此作业域其实有三张主要单据：运单是票货的作业副本、运输任务是车的一趟行程、司机作业单是人的一份待办，再加上第 3 章订单域那张商务订单，四者通过 ID 层层关联——这就是 TMS 单据体系的全貌。

## 小结：一张表教我的建模课

拆完这张表，我最大的体会是：好的领域建模，本质是在回答"这个业务里有哪些彼此独立、变化节奏不同的维度"。运输任务把执行进度、资源分配、装载程度拆成三个正交状态，把四个节点的计划与实际拆成八个时间字段，再用照片和坐标给交接动作留证——业务一复杂，表就该长这样，而不是用一个万能 status 字段硬扛。

至于这张任务表上最关键的"发车 → 到达 → 交付"三次状态流转是怎么保证并发安全的（两个调度员/司机同时操作会不会翻车），我留到第 7 章讲乐观锁时细说。
