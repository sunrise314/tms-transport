# 资源分配与状态流转：车次车辆司机匹配与乐观锁

上一章的路线规划，回答的是"走哪条路"。但线路是抽象的——"北京到上海这条干线"每天可能有好几班，真正要发车，还得回答三个具体问题：**坐今天几点的班次？派哪辆车？哪个司机开？** 这就是第四阶段资源匹配要干的活，实现在 `TaskTripsSchedulingServiceImpl`。

而任务派下去之后，司机在手机端依次做发车、到达、交付三个确认动作。这三个动作隔着几百公里、可能被重复点击、被并发触发，怎么保证状态不会错乱？这就要靠运输任务那套"状态机校验 + 乐观锁"的双保险。

这一章前后两段，分别讲资源怎么匹配、状态怎么安全流转。

## 三级模型：线路、车次、车人绑定

先理清主数据层级，否则代码读不懂。这里有三级概念：

- **运输线路（TransportLine）**：抽象的通道，比如"北京转运中心 → 上海转运中心"，带着距离成本。
- **车次（TransportTrips）**：线路下面的具体班次，挂着一个发车时刻 `departureTime`（"HH:mm" 格式）。同一条干线可以有早班、午班、晚班多个车次。
- **车次-车辆-司机关联（TransportTripsTruckDriver）**：每个车次具体绑定哪几辆车、哪些司机能跑，是一张多对多关联表。

资源匹配就是顺着这三级往下，一步步从"能走的线路"收敛到"此刻最优的一车一人"。

## 三资源过滤：车要可用、人要在岗

`execute` 方法对每一条已定好线路的订单组依次处理。先根据线路查它下面的所有车次，再查这些车次绑定的车和司机，然后进入关键的过滤方法 `getTripsTruckDriver`。这个方法的职责是：把"车、人都处于可用状态"的组合挑出来。

```java
// 获取全部车辆，只留状态正常的车（status == 1）
List<String> truckIds = truckDtos.stream()
    .filter(item -> item.getStatus() == 1)
    .map(item -> item.getId()).collect(Collectors.toList());

// 查这批车次绑定的司机，只留在岗（status 为 true）的
List<UserDTO> users = userFeign.list(driverIds, null, null, null);
if (users == null) { users = new ArrayList<>(); }   // 远程失败降级，防 NPE
List<String> userIds = users.stream()
    .filter(item -> Boolean.TRUE.equals(item.getStatus()))
    .map(item -> item.getId().toString()).collect(Collectors.toList());

// 车和司机同时可用，才算一个可行的「车次-车-司机」组合
transportTripsTruckDriverDtoList.forEach(item -> {
    if (userIds.contains(item.getUserId()) && truckIds.contains(item.getTruckId())) {
        tripsTruckDriverDTOS.add(
            new TripsTruckDriverDTO(tripsId, item.getTruckId(), IdConvert.toLong(item.getUserId())));
    }
});
```

车辆数据在 `pd-base`、司机数据在 `pd-auth`，都得跨服务 Feign 去查，这里又能看到第 2 章讲的类型边界——车次、车辆 ID 是 `pd-base` 的 String，落库前要 `IdConvert.toLong`，而司机 ID 内部本来就是 Long。

两个过滤条件看着简单，却是调度能不能落地的命门：一辆正在维修的车（status≠1）不能派，一个休假或停用的司机不能派。任何一方不可用，这个组合就得被剔掉。如果剔完之后一个可行组合都不剩，`execute` 直接 `return`——这条订单组这轮就匹配不到资源，它的运输任务会停在上一章说的 `assignedStatus = 待人工分配`，被推给调度员手工处理。**系统自动化能覆盖大多数情况，但必须诚实地标出"我搞不定、需要人"的那部分，而不是硬塞一个无效资源。**

代码里对远程调用失败也有防备：`userFeign.list` 若因下游故障走了降级返回 `null`，这里按"没有可用司机"处理而不是直接调方法炸出 NPE；注释还特意区分了"null（远程挂了）"和"空列表（确实没人）"两种语义。

## 选最优班次：发车时间最近者优先

经过过滤可能得到好几个可行组合（早班小王开 A 车、午班老李开 B 车……），选哪个？`getBestTripsTruckDriverDTO` 的策略很贴合实际——**选当前时刻之后最近发车的那一班**：

```java
LocalDateTime nowDate = LocalDateTime.now();
// 所有车次按发车时刻升序
for (TransportTripsDto item : transportTripsDtos.stream()
        .sorted(Comparator.comparing(TransportTripsDto::getDepartureTime))
        .collect(Collectors.toList())) {
    String[] departures = item.getDepartureTime().split(":");
    LocalTime departureTime = LocalTime.of(Integer.parseInt(departures[0]),
                                           Integer.parseInt(departures[1]));
    LocalDateTime departureDate = LocalDateTime.of(LocalDate.now(), departureTime);
    // 发车时刻统一换算后与当前时间比较
    long minute = Duration.between(nowDate, DateUtils.shanghaiToUTC(departureDate)).toMinutes();
    if (minute > 0) {            // 这一班还没发，且是排序后第一个，即"最近的未来班次"
        tripsTruckDriverDTO = ...;
        break;
    }
}
if (tripsTruckDriverDTO == null) {
    tripsTruckDriverDTO = tripsTruckDriverDTOS.get(0);  // 今天的班次都过点了，兜底用第一个
}
```

逻辑是把每个车次的"今天 HH:mm"补成完整时间、换算时区后和"现在"比，排序后第一个还没发车的班，就是等待时间最短的最优解。这样货能赶上最早一班可发的车，减少在网点的滞留。如果今天所有班次都已经过了发车点（`minute > 0` 一个都没命中），就兜底取第一个方案，不致于空手而归。

选定后，`relation` 把"订单分类 → 车次/车/司机"的绑定写进关联表 `disp_order_classify_attach`，第五阶段再据此回填运输任务、生成司机作业单。到这儿，一批订单才真正从"纸面线路"落到了"具体的车和人"。

## 三态流转的并发隐患

资源匹配完成，运输任务进入执行期。司机在手机端会依次触发三个动作：`depart`（发车确认）、`arrive`（到达确认）、`deliver`（交付确认），对应状态的 1→2→3→4。

这三个写操作有真实的并发风险。设想：网络卡顿，司机对着"发车"按钮连点两下，两个请求几乎同时到达；或者调度后台和司机端在同一刻操作同一任务。如果不加防护，可能出现重复扣减、状态回退、一条任务被处理两遍。

品达的做法是**两道保险**。

**第一道：应用层状态机校验。** 在真正更新前，先读出任务当前状态，交给 `StateTransitionValidator` 判断"当前状态能不能流转到目标状态"。这个校验器内部用一张映射表定义了全部合法流转：

```java
TRANSPORT_TASK_TRANSITIONS.put(PENDING.getCode(),    new HashSet<>(singletonList(PROCESSING.getCode()))); // 1→2
TRANSPORT_TASK_TRANSITIONS.put(PROCESSING.getCode(), new HashSet<>(singletonList(CONFIRM.getCode())));    // 2→3
TRANSPORT_TASK_TRANSITIONS.put(CONFIRM.getCode(),    new HashSet<>(Arrays.asList(COMPLETED.getCode(), CANCELLED.getCode()))); // 3→4/5
TRANSPORT_TASK_TRANSITIONS.put(COMPLETED.getCode(),  Collections.emptySet());  // 终态
TRANSPORT_TASK_TRANSITIONS.put(CANCELLED.getCode(),  Collections.emptySet());  // 终态
```

待执行只能去进行中、进行中只能去待确认、待确认可以完成或取消，已完成和已取消是终点，谁也别想再动。这张表把状态机的"拓扑"集中声明，代码里不允许出现任何跳跃式更新。值得一提的是，这个校验器配套写了单元测试，专门断言"1→2 合法、2→3 合法、已完成→已取消非法"，状态机这种东西，有测试兜底才敢在重构时放心改。

**第二道：数据库层乐观锁（CAS）。** 光有应用层校验还不够——两个请求可能都通过了校验（读到的都是状态 1），然后排队去更新。真正拦住并发的是更新语句本身。看 `depart`：

```java
// 发车确认：状态 待执行(1) → 进行中(2)
LambdaUpdateWrapper<TaskTransport> wrapper = new LambdaUpdateWrapper<>();
wrapper.eq(TaskTransport::getId, id)
       .eq(TaskTransport::getStatus, TransportTaskStatus.PENDING.getCode()) // 关键：带状态条件
       .set(TaskTransport::getStatus, targetStatus)
       .set(TaskTransport::getActualDepartureTime, LocalDateTime.now())
       .set(TaskTransport::getUpdateTime, LocalDateTime.now());
boolean result = update(wrapper);
```

翻译成 SQL 就是 `UPDATE work_task_transport SET status=2, actual_departure_time=? WHERE id=? AND status=1`。这就是乐观锁的经典写法——**更新时把"我以为的当前状态"也放进 WHERE 条件**。两个并发请求都以为状态是 1，第一个执行成功、把状态改成 2；第二个再执行时 `WHERE status=1` 已经匹配不到行，影响行数为 0，`update` 返回 false，重复操作就此落空。这种"比较并设置"（Compare-And-Set）的手法不需要显式版本号列，因为状态字段本身就充当了版本标记，非常适合这种单向推进的状态流。

`arrive`（2→3，写实际到达时间）和 `deliver`（3→4，写实际交付时间）是一模一样的写法，只是 WHERE 里的期望状态换成进行中、待确认。

## 每一次流转都要留痕

状态改成功之后，代码还做了一件重要的事——往审计表 `work_status_transition_history` 写一条流转记录：

```java
statusTransitionHistoryService.recordTransition(
    BUSINESS_TYPE_TRANSPORT_TASK, id, String.valueOf(id),
    taskTransport.getStatus(), targetStatus,
    getCurrentOperatorId(), getCurrentOperatorName(), getCurrentOperatorType(),
    "发车确认");
```

谁（操作人 ID、姓名、类型）、在什么时候、把哪条单据、从什么状态改成了什么状态、因为什么动作，全部留痕。物流是多方协同、纠纷高发的行当，"这趟车到底是谁点的发车、几点确认到达"必须能倒查。状态流转审计和第 4 章讲的四张交接照片、两副坐标一起，构成了完整的责任证据链。

最后，交付确认（`deliver`）成功后还有一个收尾动作 `syncStatusOnComplete`：运输任务完成，要把挂在它上面的运单、进而把 `pd-oms` 里的订单联动推进到"已签收"，并触发第 10 章要讲的结算单生成。这个联动被包在 try-catch 里——联动万一失败，只记错误日志、不影响交付确认本身的成功提交。这是个很成熟的取舍：主操作（司机交付）已经真实发生且不可撤回，不能因为下游通知失败就把主操作也判成失败，否则会出现"货明明交到了、系统却说没交付"的荒谬状态。联动失败应该靠补偿或对账去追，而不是反向拖垮主事务。

至此，从下单到调度再到在途执行的主干就全部打通了。但我们一直假设系统"知道车在哪"——这个能力还没揭开。接下来两章进入轨迹域，先看 `pd-netty` 怎么用 Netty 接住成百上千辆车的长连接，又是怎么用消息队列把洪峰般的 GPS 点位削平的。
